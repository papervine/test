Papervine exposes [Model Context Protocol](https://modelcontextprotocol.io/) servers so AI
tools can both **read** a docs site and **edit** it — two distinct MCP servers. The two have
very different maturity and trust models.

<Info>
  Both are **built**. The read MCP is auto-generated per site and needs no auth. The authoring
  (write) MCP shares its backend with the [web editor](/control-plane/editor) and is
  authenticated — today via the dashboard session; token-scoped external access
  ([platform-auth](/auth/platform-auth)) is the follow-up.
</Info>

## Generated read MCP (per docs site)

Every published site gets a read MCP server automatically — no authoring step. It is for the
*readers'* AI tools (Claude, Cursor, Windsurf) and exposes the **same tool layer as the
[AI assistant](/features/ai-assistant)** — `search_docs`, `read_page`, `list_pages`, and
`search_api` — over Streamable HTTP at `https://{tenant}/mcp`. One implementation, two
transports (in-docs chat and MCP).

<Note>
  This is not hosted-only. The [CLI](/cli) serves the same four tools at `/mcp`, so
  `papervine dev` gives your editor's AI a live view of the docs you are writing, and
  [`papervine serve`](/guides/self-hosting) gives a self-hosted site the same endpoint a hosted
  one has. The tool names, descriptions and schemas are shared code, so a client sees the same
  server either way — what the hosted version adds is tenant routing, the reader-auth gate, and
  agent analytics.
</Note>

<Warning>
  Because the CLI has no reader auth, its MCP server applies **no gate**: `list_pages` returns
  every page and `read_page` will read one marked `groups: [...]`. On a hosted site the same tools
  see only the public subset. So if you self-host a repo with gated pages, the MCP endpoint
  enumerates them — see [self-hosting](/guides/self-hosting).
</Warning>

Connect any MCP-capable tool to `https://<host>/mcp`:

<Steps>
  <Step title="Point your tool at the endpoint">
    Add `https://<your-docs-host>/mcp` as a Streamable HTTP MCP server in Claude, Cursor, or
    Windsurf — or `http://localhost:3000/mcp` against a running `papervine dev`.
  </Step>
  <Step title="The model lists and calls tools">
    It sees `search_docs`, `read_page`, `list_pages`, and — only when the site references an
    OpenAPI spec — `search_api`.
  </Step>
  <Step title="Retrieval runs over published content">
    The same index the docs site uses, scoped to that tenant.
  </Step>
</Steps>

What ships today:

- **Streamable HTTP server at `/mcp`** (stateless), exposing the four tools. `search_api`
  appears only when the site has an OpenAPI reference. The tools are the *shared* docs-tools
  capabilities — the same code the assistant calls.
- **Tenant-routed and instrumented.** The endpoint serves on the tenant host and resolves the
  right content source per connection. Each connection logs agent analytics: `search_docs`
  becomes an MCP-search event and `read_page` becomes an agent page view
  (`source:"agent"`), which feeds the Agents tab in [Analytics](/control-plane/analytics).
- **`llms.txt`.** For clients that don't speak MCP, every site also publishes a plain-HTTP
  feed of the same content: an index at `/llms.txt`, the whole corpus at `/llms-full.txt`, and
  a Markdown twin of every page at `<path>.md`. See
  [llms.txt and .md pages](/features/llms-txt).

Indexing follows the same [freshness rules](/features/ai-assistant#indexing-and-freshness) as
the assistant — published pages + OpenAPI specs, excluding hidden/`noindex`.

<Note>
  Still to come for the read MCP: a `docs.json` opt-out and per-tenant rate limits; live API
  execution as MCP tools (which depends on the "Try it" auth/proxy work, see the
  [API playground](/features/api-playground)); and building the index at sync time.
</Note>

## Authoring MCP (admin / write)

The authoring MCP lets a docs *owner* connect an AI tool to **edit their docs** (an admin
MCP). It is the agent-native counterpart to the [web editor](/control-plane/editor): any
action an owner can take in the editor, an agent can take through this MCP — they share one
backend.

<Warning>
  Edits happen on a **session branch** and land via **commit or Pull Request** — never silently
  on the deploy branch. The authoring MCP is authenticated: it requires a dashboard session and
  the `x-papervine-org` / `x-papervine-site` headers naming the target site, with the editor
  feature enabled for your role. Token-scoped external access ([platform-auth](/auth/platform-auth))
  is the follow-up.
</Warning>

It serves at `/authoring/mcp`. The tools, grouped by what they touch:

- **Content** — `read`, `search`, `list_pages`, `write_page` (full MDX), `edit_page` (a
  targeted find/replace on the raw MDX).
- **Git** — `save` (`mode: "pr" | "commit"`). A working branch is checked out automatically on
  first use (or named via the `x-papervine-branch` header).

Editing the `navigation` structure and `docs.json` from the MCP (`create_node` / `move_node` /
`update_config`) is a planned extension.

### One backend, two front-ends

The authoring MCP and the web editor are **not separate write paths**. They operate on the
**same session branch and the same server-side draft buffer**:

- `checkout`'s response includes an `editorUrl` you can open to "follow along" in the
  dashboard editor on that same branch.
- Edits **buffer on the session branch in real time**, persisted server-side across tabs and
  devices.
- Nothing reaches the deploy branch until `save` / publish — a **direct commit** if you're on
  the deploy branch, otherwise a **PR** with a returned link.

The draft buffer is real persistent state, not a commit-on-save shortcut. The authoring layer
is written once — GitHub-App write creds → session branch + draft buffer → `save` as
commit-or-PR — and both the MCP and the [web editor](/control-plane/editor) sit on top of it.

## Read vs. authoring at a glance

<CardGroup cols={2}>
  <Card title="Read MCP">
    Auto-generated per site. No auth. Read-only retrieval (`search_docs`, `read_page`,
    `list_pages`, `search_api`). For docs *readers'* tools. **Shipped.**
  </Card>
  <Card title="Authoring MCP">
    Owner-connected, authenticated. Reads + writes (`write_page`, `edit_page`, `save`) via a
    session branch → commit/PR. Shares the editor's backend. For docs *owners*. **Built.**
  </Card>
</CardGroup>
