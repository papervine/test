The **Automate** rail groups the three surfaces where Papervine *acts on* the docs rather than
just rendering them: **Automations** (scheduled and triggered agent runs), **Agent** (the chat
agent), and **Assistant** (the in-docs reader assistant). All three are gated behind a per-org
**Trialing** entitlement.

<Note>
  **Automations and the Agent answer questions; most of the connector catalog is still UI
  only.** Automations can be configured, toggled, and run; a connected Slack workspace can ask
  the agent questions about the docs; and Google Drive can be connected as a source it reads.
  Not yet wired: the remaining connectors under *Available to your team*, and asking the agent
  to *change* the docs from Slack. Parts of the Assistant page persist
  while others are scaffold (see [below](#where-each-toggles-state-lives)). Where the spec and
  the implementation diverge, the spec wins.
</Note>

## Why one section

Automations, the Agent, and the Assistant all run Claude over the tenant's content with tools, and all
three write through a **single shared authoring backend**: GitHub-App write credentials → a
session branch → a draft buffer → `save` as a commit or PR. This is the same pipeline as the
[authoring MCP](/features/mcp-servers) and the web editor — never a parallel write path. Under
the hood they share one *run primitive* — `{ trigger, context, prompt, applyMode, output }` —
with three frontends: scheduled/triggered (Automations), interactive from chat (Agent), and
in-docs Q&A (Assistant).

## Automations

Agent runs that keep the docs current on their own: each automation is a trigger, a prompt, and
an apply mode. When it fires, an agent reads the site's content and makes the required edits on a
draft session branch — the same authoring pipeline a human editor uses. Depending on the apply
mode, the result either **commits directly** or **waits for your review** in the editor.

The page has two tabs: **Configure** (the catalog below) and **Runs** (the run history —
every run with its status, what fired it, its result, credits used, and the agent's summary or
the error). A run that finishes without needing any edits shows as **no changes** — a real
outcome, not a failure; a run awaiting review shows **review needed**. **Click a run** to open
its detail view: the exact instructions the agent received (the run keeps its own copy, so later
config edits don't rewrite history), the files it changed, the full agent summary, model and
token usage, and the resulting commit — or, for a pending run, the review actions.

A run's **Result** depends on where your content lives. On a Git-backed site it's the commit or
the pull request the run produced, linked. On a
[Papervine-hosted site](/guides/start-from-scratch) there's no commit to link, so a run that
changed something reads **Published to the live site** — and **no changes** means exactly that:
the agent looked and found nothing to fix.

Both the run list and a run's detail view update live as it progresses — queued, running,
succeeded/failed/review needed — with no manual reload, whether you triggered it yourself or a
scheduled/webhook trigger fired it while you were watching.

### The catalog

Two built-in families, plus custom:

A **custom automation** is the same configuration with your own name and prompt. Flipping any
card's toggle on creates it with recommended defaults; the gear opens its settings.

### Configuration

Every automation — predefined or custom — shares one config schema:

- **Trigger** — `Content update` (fires when a sync publishes new content), `Custom schedule`
  (a cron expression, with presets), or `Code change` (fires when a push lands on a **trigger
  repository** — typically a product's source repo whose merged PRs should update the docs).
  Each catalog entry offers the triggers that make sense for it and recommends one.
- **Trigger repositories** (`Code change` only) — the `owner/name` source repos whose pushes
  fire the automation. When one is pushed, the run is told which files changed and can read
  them to update the affected documentation.
- **Apply mode** — `Automatically` commits changes directly to the deploy branch;
  `Require review` holds the change as an **in-app draft** for you to review before it lands
  (see [Reviewing a change](#reviewing-a-change) below).
- **Context repositories** — extra `owner/name` repositories the run may read (never trigger
  it), so the agent can consult their code while writing docs.
- **Additional prompt** — instructions appended to the automation's base prompt on every run
  (voice, formatting rules, edge cases to watch for).

<Note>
  **Code-change triggers and context repositories need the GitHub App.** Push webhooks only
  arrive from the App, and the run reads other repositories with the App's installation token
  — a personal-access-token or public connection has neither. Connect the site with the GitHub
  App to use these; the automation's configuration form says so if it isn't. The repositories
  are read-only to the agent: its only way to change anything is the documentation itself.
</Note>

Enabled automations also expose **Run now** — a manual trigger, which is also how you test one.
Triggering one confirms with a **View run** button that takes you straight to the run it queued,
so you can watch it progress rather than hunting for it in the Runs tab.

### How runs execute

Runs don't happen in your browser. Each one is queued and picked up by a background executor,
so closing the tab doesn't stop a run and a long run can't time out a page — you watch progress
in the Runs tab, or follow the **View run** button straight to it.

If a deployment has no executor configured, the Automations page tells you so and automations
simply don't run. Nothing else in the dashboard or the renderer depends on one, so it's a
feature you can leave off rather than a piece that has to be working.

<Note>
  **Self-hosting?** The executor is a separate deploy from the web app, and forgetting its
  release step leaves runs stuck **pending** — see
  [Background services](/background-services#the-automations-executor).
</Note>

Because the executor runs in its own environment, it also needs its **own copy of the server
configuration** — it does not inherit the web app's. A run reaches the database, the draft
storage, the model provider, and the connected repositories, so the executor's environment must
carry the same database URL, object-storage credentials, AI configuration, and GitHub-App keys
the app uses. A missing value surfaces as a run that fails immediately on its first step rather
than as a degraded feature. This project keeps the two environments in sync automatically at
deploy time; an executor you run yourself is configured wherever its tasks are deployed.

Each run is metered: its
model usage is recorded and debited against the plan's [AI credits](/control-plane/billing),
and the total shows in the run history. A run whose organization has no spendable credits
fails immediately with "out of AI credits" — before any model call, so a drained account
never accrues charges it can't pay.

Scheduled automations register their cron expression with the executor when you save them,
and re-register when you change the schedule. Each tick re-reads the automation from the
database before doing anything, so an automation you disabled or re-triggered stops running
even if its schedule outlives it. Ticks are deduplicated by their timestamp: a redelivered
tick never runs twice.

### Reviewing a change

When an automation runs with `Require review`, its edits **don't ship** — they wait as a draft
for you to approve. The run lands as **review needed** in the history, with three actions:

- **View changes** opens the change in the [editor](/control-plane/editor), landing on the first
  edited page with the diff already showing — the same live editor a human uses, so you can also
  keep editing the draft before accepting.
- **Accept** commits the change to your deploy branch (the same as an `Automatically` run would).
- **Reject** discards the draft; nothing lands.

The draft lives in the authoring layer as an ordinary edit session until you decide, so a pending
review is just a draft with your name not yet on it. Until then it hasn't touched your published
docs. (A pending review doesn't block the automation's next scheduled run — accept or reject it to
keep the queue clear.)

### What keeps runs from wasting credits

An agent run is the expensive part of Papervine — it reads your documentation and reasons
over it across many model calls. Three things keep that from turning into a surprise bill:

- **Unchanged docs don't run.** Before an automated run starts, Papervine compares your
  site's current commit with the one its last successful run saw. If nothing has changed,
  the run is skipped entirely — no model call, no credits, no history entry. A nightly
  schedule on documentation nobody edited costs nothing. This applies to automations that
  only read your docs (the maintenance family); automations that also read a source
  repository, assistant conversations, or reader feedback always run, because their input
  can change while your docs sit still.
- **A daily run limit.** Each automation runs at most 500 times a day. Runs that fail
  before reaching the model don't count against it, so a misconfigured schedule can't
  drain an account and a broken automation can still retry. **Run now** is never blocked
  by the limit — you asked for that one.
- **Prompt caching.** Within a run, the instructions and tool definitions that stay
  constant are cached, so the repeated context across a run's steps is billed at a fraction
  of the normal input rate. Caching is provider-agnostic through the AI gateway — it applies
  automatically whatever model you configure, so choosing a cheaper model keeps the discount
  rather than trading it away.

Clicking **Run now** always executes, even when a scheduled run would have been skipped —
useful when you want to re-check a site you haven't edited.

A content-update automation whose own commit re-syncs the site does **not** re-fire itself:
runs are deduplicated per commit, which is also what makes webhook redeliveries harmless.

<Warning>
  The open risk is the **output quality and auditability** of agent-authored changes. Every run
  lands through the same authoring pipeline a human uses, so its changes are reviewable in the
  editor and in Git history — but an automation that drafts low-quality updates at scale is noise.
  Prefer `Require review` until you trust an automation's output.
</Warning>

## Agent

An interactive agent reachable from chat. The surface is **Slack-centric**: you invoke it with
`@papervine <prompt>` in a channel, and the agent answers questions and opens doc changes on
request.

The **Agent settings** page is where you wire it up. A **Connect your Slack workspace** banner
installs the Slack app — the agent's home. Below it, **Enabled integrations** lists the
connectors the agent can currently draw on (empty until you connect one), and **Available to
your team** is the catalog of connectors you can add — Notion, Google Drive, Linear, Jira,
Confluence, Salesforce, HubSpot, Intercom, Plain, and more — each grouped by what it brings
(documentation, communication, project management, customer support, CRM). Connecting a source
lets the agent reference it when it answers and authors.

It shares the authoring backend with Automations — the distinction is **interactive (Agent) vs
scheduled/triggered (Automations)**, over the same underlying tools.

<Info>
  **Why Slack.** The reference product treats Agent as "your docs teammate in Slack" — it lives
  where the team already works rather than as a separate console, and threads give it
  conversational context and an audit trail for the PRs it opens. Open question: whether to also
  offer Teams, Discord, or a web console, or keep Slack the canonical home.
</Info>

### Connecting Slack

The Slack connection is a **per-organization install** of the deployment's own Slack app:
**Install Slack app** sends a workspace admin through Slack's consent screen, and on approval
Papervine stores the workspace's bot credential encrypted, ties the workspace to your
organization, and the banner flips to **Connected** with the workspace's name. **Reinstall**
re-runs the same flow (refreshing the credential and any newly required permissions);
**Disconnect** removes the workspace link immediately — either that, or removing the app from
Slack's side, is enough on its own to stop the agent.

Self-hosting? The Slack app itself is created once from the `slack-app-manifest.json` at the
repository root and configured through the `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`, and
`SLACK_SIGNING_SECRET` environment variables — unset, the banner reads **Not configured** and
the rest of the dashboard is unaffected. The install callback lives on the app host (it needs
your dashboard session to know which organization is installing); Slack requires an `https`
redirect URL, so local development needs a tunnel or its own development Slack app.

### Asking the agent something

Once a workspace is connected, mention the bot in any channel it's in — `@papervine how does
reader auth work?` — or send it a direct message, where no mention is needed. It replies **in
a thread**, never at the channel's top level, so a question and its answer stay together.

What happens next: the agent searches your published documentation, reads the pages it needs,
and answers from what it finds, linking the pages it used. It reads the **live** docs — the
same content your readers see, not an in-progress draft — and it only reads: asking it to
*change* the docs from Slack isn't wired yet. If your documentation genuinely doesn't cover
something, it says so rather than guessing, which is also a useful signal about what to write
next.

The reply posts as a placeholder that turns into the answer, because a question can take up to
a minute to research. That work happens on the same background executor automations use, so a
long answer can't be cut short by a timeout — and if a deployment has no executor configured,
the agent simply doesn't answer (nothing else breaks).

Each answer is metered against your plan's [AI credits](/control-plane/billing), exactly as an
automation run is, and there's a generous daily ceiling per organization so a runaway loop
can't drain an account. A retried Slack delivery never produces a second answer: each message
is answered once.

### Connecting a source

*Available to your team* lists the services the agent can draw on beyond your documentation.
**Google Drive** and **Notion** work today; the rest of the catalog reads **Coming soon** until
its connector lands, so you can see what's planned without being offered a button that would
only fail.

Connecting takes one click: a popup runs that provider's own sign-in, and the connection moves
up into **Enabled integrations** with a line describing what the agent can do with it. Only
owners and admins can connect a source, because connecting grants the agent live read access to
whatever the authorizing account can open — connect it as an account whose reach you're happy
for the agent to have.

**Papervine never holds the credential.** It goes straight from the provider into the
integrations vault, and we keep only a handle. That's also what makes disconnecting immediate
rather than eventual: **Disconnect** revokes the grant at the source and removes the connection,
and the agent loses those tools on its very next question. Nothing is copied or indexed in the
meantime — every read is a live call at the moment the agent asks, so what it can see is exactly
what the connected account can see, right now.

With **Google Drive** connected the agent can search the Drive and read documents — Google Docs,
Sheets and Slides included, and shared drives as well as personal ones. With **Notion**, it can
search the workspace and read a page's content.

Notion has one behaviour worth knowing, because it surprises people: Notion only exposes pages
that have been **explicitly shared with the integration**, which is narrower than "the
workspace". If the agent reports finding nothing, that's the usual reason — share the relevant
pages or their parent, and search again.

Whatever the source, the agent will tell you which one an answer came from, and that matters: a
Drive file or a Notion page isn't documentation, and an answer drawn from a stale internal
document shouldn't read like published guidance. It prefers your docs when they cover the
question, and a long document is truncated rather than quoted whole (it says when that happens).

<Note>
  Self-hosting? Connectors need an integrations backend configured (`NANGO_SECRET_KEY` and a
  webhook secret) — see `.env.example`. Unset, the gallery says so and the rest of the Agent
  page works normally. The executor needs the same key, since the connector tools run inside
  the agent's background task.
</Note>

## Assistant

The management page for the **same in-docs [AI assistant](/features/ai-assistant)**, surfaced
under Automate. This is not a fourth system — it is the settings surface the assistant calls
for. The layout:

- A **usage overview** strip (Total questions / Answered properly / Not Answered, each with a
  vs-last-month delta) plus a "Get insights" card linking to the
  [Analytics](/control-plane/analytics) deep-dive. The overview is cross-linked, not
  duplicated.
- **Status and control** — an enable/disable toggle with an Active/Inactive badge.
- **Response handling** — deflection to a support email and a "show help button", with **Search
  Domains** gated behind an enterprise-plan upsell.
- **Bot protection** — an invisible hCaptcha toggle.
- **Starter questions** — up to three.

### Where each toggle's state lives

The Assistant page mixes two kinds of setting, and they're stored differently on purpose:

- **Operational toggles — *Status* and *Invisible CAPTCHA* — are database state.** They're a
  kill switch and an abuse guard, so they take effect **instantly, with no Git commit**. The
  toggles persist the moment you flip them (the same instant-effect path as
  [reader authentication](/auth/reader-auth)): the switch reflects the stored value, a click
  writes it, and a reload re-reads it. The Status badge tracks the toggle (Active when on,
  Inactive when off). Turning *Status* off is enforced on the live docs site: the **Assistant
  Assistant** launcher stops rendering and the assistant endpoint declines requests, so a
  disabled assistant truly disappears for readers. *(Search Domains and Starter Questions are
  scaffold today, so their switches don't yet change reader behavior; CAPTCHA persists but
  its enforcement is still to come.)*
- **Published-behavior settings — deflection, search domains, starter questions — are
  version-controlled in `docs.json`.** They describe what readers see, so they belong in Git
  and are edited through the [authoring layer](/features/mcp-servers) rather than written to a
  database column. These controls are still scaffold on this page until that write path is
  surfaced here.

Running your own deployment gets the same split from configuration alone: the operational
state from environment, the published behavior from `docs.json` — no dashboard required.
