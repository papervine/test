This page is for whoever **operates** the multi-tenant platform. If you self-host the
renderer or use the CLI, there is no billing at all and nothing here applies — see
[Plans & billing](/control-plane/billing) for the customer-facing behaviour.

## Autumn is the source of truth

Plans, entitlements, prices, credit packs and the trial are configured in
[Autumn](https://useautumn.com), which sits above Stripe and provisions the Stripe
products, prices, subscriptions and invoices from them. Papervine reads that state and
enforces it; it does not keep its own copy.

That means **editing a plan in Autumn is the deploy**. There is no catalog to sync, no
publish step, and no Stripe webhook of our own — Autumn keeps subscription state, usage
and access in step without one.

The same goes for support work. Putting an organization on a plan without charging it,
adjusting a credit balance, reading an invoice or a subscription's history — all of it is
done in Autumn's dashboard, which records who did what. Papervine has no billing console
of its own: the operator console links to Autumn, and every organization's page there
links straight to its customer record (customers are keyed by the organization id, and
carry the organization's name and its owner's email so they can be found by either).

<Note>
  One thing is deliberately not in Autumn: the marketing copy on the public pricing page.
  Plan names, feature bullets and the comparison table live in
  `src/lib/billing/catalog.json` and ship with a deploy, because Autumn stores no
  marketing text. **The prices on that page ship with it too** — the public page has to
  render with no API key and no network — so a price change in Autumn needs the same
  change committed here, or the storefront and the checkout disagree.
</Note>

## Configuring it

<Steps>
  <Step title="Create the environment">
    Autumn has separate sandbox and production environments, each with its own catalog.
    Connect the Stripe account you want that environment to bill through.
  </Step>
  <Step title="Set the key">
    Put the environment's secret key in `AUTUMN_SECRET_KEY`. The key selects the
    environment — there is no separate mode flag.

    ```bash
    AUTUMN_SECRET_KEY=am_sk_test_...
    ```
  </Step>
  <Step title="Match the plan ids">
    The application refers to two plans by id: `free` (auto-enabled for every new
    customer) and `pro_trial` (the limited-time trial attached at signup). Credit
    balances are the `ai_credits` feature, and every plan entitlement maps to a feature
    id — `sso`, `rbac`, `writer_agent`, `white_label` and so on. Renaming one of these in
    Autumn without renaming it in `src/lib/billing/autumn.ts` makes the feature read as
    *not granted*.
  </Step>
</Steps>

## Backfilling existing organizations

A customer is created in Autumn lazily: when an organization is created through the
product, and on its first billing action. An organization that predates billing, or one
inserted straight into the database, has no customer and resolves to the Free floor with
nothing metered. The sync script creates the missing ones:

```bash
node --env-file=.env.local scripts/sync-autumn-customers.mjs            # dry run
node --env-file=.env.local scripts/sync-autumn-customers.mjs --apply    # create them
node --env-file=.env.local scripts/sync-autumn-customers.mjs --apply --trial
```

It reads every organization from `DATABASE_URL`, sends the same fields the application
sends (the organization id as the customer id, the organization name, the owner's email),
and is idempotent: a customer that already exists is reported and left alone. `--trial`
attaches the 30-day trial to each customer the run creates — what a new organization gets
at signup — and never to one that already existed. Nothing is ever deleted.

Which environment it writes to is decided by `AUTUMN_SECRET_KEY` alone, and the script
prints both the Autumn environment and the database host before touching anything, so a
mismatched pair is visible rather than silent. The same script therefore serves every
pairing: a development database into the sandbox while testing, and the production
database into the live environment once the key is switched.

<Note>
**Local development.** `npm run db:seed` runs this sync itself when `AUTUMN_SECRET_KEY` is a
sandbox key, so the seeded organization arrives in Autumn on the trial with no extra step.
The seed refuses to write to the live environment.
</Note>

## Webhooks

Autumn can tell Papervine the moment an organization's plan or balances change. Register
`https://<your app host>/api/webhooks/autumn` as a webhook endpoint in Autumn — once per
environment — and put the endpoint secret Autumn shows (`whsec_…`) in
`AUTUMN_WEBHOOK_SECRET`.

With it configured, a delivery does two things and writes nothing: it drops the
organization's cached billing read, and it signals any dashboard that organization has open,
which re-renders in place. A page showing "Automations come with Pro" becomes the real
Automations page as the upgrade lands; the rail's trial pills disappear when a trial ends.

Without it, nothing breaks. Dashboard reads are cached for at most a minute, so any
navigation shows the new state within that window. Deliveries are verified by signature;
unsigned or badly signed requests are refused, and a registered URL with no secret answers
503 so the failure is visible in Autumn's delivery log rather than silent. Realtime
re-rendering also needs the realtime service configured; without it the cache drop alone
still makes the next navigation correct.

### Testing it locally

Autumn cannot reach `app.localhost`, so a change made in the sandbox dashboard shows up
locally only when the cache expires — about a minute, then a reload. The Svix CLI closes
that gap the way `stripe listen` did for Stripe: it gives you a public relay URL that
forwards deliveries, headers intact, to your dev server.

<Steps>
  <Step title="Install the CLI and mint a relay">
    ```bash
    brew install svix/svix/svix-cli
    svix listen http://127.0.0.1:3000/api/webhooks/autumn
    ```
    It prints a relay URL (`https://play.svix.com/in/…`) and the token behind it. Stop it
    once you have both.
  </Step>
  <Step title="Register the relay in Autumn's sandbox">
    Add the relay URL as a webhook endpoint in the **sandbox** environment and copy the
    endpoint secret it shows.
  </Step>
  <Step title="Put both in .env.local">
    ```bash
    AUTUMN_WEBHOOK_SECRET=whsec_…
    AUTUMN_WEBHOOK_PLAY_TOKEN=c_…
    ```
    `npm run dev` now starts the relay alongside the app and reconnects to the same URL
    every time, so the registration is a one-off. Change a plan in the sandbox and the open
    dashboard re-renders.
  </Step>
</Steps>

Keep the sandbox and live endpoints separate: each environment has its own secret, and a
live delivery signed with the sandbox secret is refused. The route ignores the request's
hostname, so any relay or tunnel works without a host-header rewrite.

## What happens without a key

Leaving `AUTUMN_SECRET_KEY` unset is a supported state, not a broken one — it is how
renderer work, `npx papervine dev` and CI all run.

- Docs sites render exactly as normal. Billing is never on the render path.
- Every organization resolves to **Free**: AI features are gated off, and nothing meters.
- Settings → Billing reports that billing is not configured; no plan can be purchased.
- The "Powered by Papervine" badge follows the Free plan.

## When Autumn is unreachable

A billing outage must never take down a surface someone paid for, so the failure
directions are chosen rather than incidental:

- **The AI gate fails open.** If the lookup fails, the request is allowed and *not*
  metered. Losing a few credits' revenue is cheaper than refusing a paying customer.
- **The badge fails toward hiding.** Showing "Powered by Papervine" on an Enterprise
  customer's white-labelled docs is a visible regression of the thing they bought;
  omitting it from a Free site for a minute costs nothing. The badge answer is also cached
  for a minute, which is what keeps a third-party API off the docs render path.
- **Metering never surfaces to the reader.** Usage is recorded after the answer has
  streamed; if the deduction fails it is logged and dropped.

## Rating stays here

Token-to-credit conversion is Papervine's, not Autumn's. The rate table is calibrated so a
typical assistant answer costs around ten credits, and it prices self-hosted inference
(the `ollama/` provider prefix) at **zero** — a customer running their own GPU costs us
nothing, and a table priced from public model rates has no way to know that. Autumn holds
the balance; we decide what an operation costs and report the number.

Usage events — which feature spent which credits, on which model — stay in Papervine's own
database. That is what the usage chart reads and what future rate calibration depends on.
