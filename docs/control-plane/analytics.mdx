The **Analytics** page reports how a site is used. It is scoped to the **active site** (the
[dashboard switcher](/control-plane/overview)) and offers a **Humans vs Agents** toggle —
human visitors versus agent/MCP traffic — plus a **date-range** picker. The
[AI assistant](/features/ai-assistant) management page links here via its "Get insights"
card.

## Humans vs Agents

A toggle splits the page into two distinct views.

<Tabs>
  <Tab title="Humans">
    Metric cards, a visitors-over-time chart, top pages, and referrals — the standard docs
    analytics for human readers.
  </Tab>
  <Tab title="Agents">
    A distinct layout for agent/MCP traffic: **Agent Visitors** and **MCP Searches** cards, an
    Agent-Visitors-Over-Time chart, and **Top pages** plus **Top agents** (Claude, ChatGPT,
    and so on). Per-page agent volume lives under Top pages — the Agents tab keeps just the
    two headline cards, with no separate agent "Views" card.
  </Tab>
</Tabs>

Agent traffic is logged live. User-agent detection names the agent; a `read_page` call, an
`/llms.txt` fetch, or a fetch of a page's `.md` twin counts as an agent page view, and a
`search_docs` call counts as an MCP search. See the [MCP servers](/features/mcp-servers),
[llms.txt](/features/llms-txt), and [search](/features/search) pages for those surfaces.

## Metric cards

Each card carries a delta versus the previous period:

- **Visitors** — distinct visitors.
- **Views** — page views.
- **Assistant** — assistant queries.
- **Searches** — search intents (see below).
- **Feedback** — 👍 / 👎 counts.

## Assistant analytics

- **Assistant Usage chart** — daily **Answered vs Unanswered** over the period, with the split
  spelled out (e.g. "Answered 5 (100%) · Unanswered 0 (0%)").
- Two tabs over the assistant conversation log, each with **Export to CSV**:

<CardGroup cols={2}>
  <Card title="Categories">
    Questions auto-clustered into labeled categories (e.g. "Understanding roles") with an
    **Occurrence** count and a **last-asked** date; rows expand to the underlying questions.
    This is the **content-gap engine**: high-occurrence and unanswered questions are the docs
    to write next. Clustering and labeling run as a scheduled Claude job.
  </Card>
  <Card title="Chat history">
    Every conversation as a **Query** plus timestamp and **Chat length** (turns); a row
    expands to the full transcript — question, answer, citations, and feedback. Browsable and
    searchable.
  </Card>
</CardGroup>

## Two counting subtleties

Analytics is only as good as what it counts. Two derivations are worth understanding because
the naive version is wrong.

### Agent visitors are distinct clients, not call counts

**Agent Visitors** is `count(distinct sessionId)` over agent page views — the agent analogue
of the Humans tab's distinct-visitor metric (which keys off a persisted `localStorage` UUID).

The MCP server is **stateless** (no Redis), so it re-instantiates per tool call. Minting a
fresh id on each call would count every `read_page` as a *new* visitor — three reads in one
Claude session would show as "3 Agent Visitors". Instead, `sessionId` is a **stable per-client
id**: the client's `Mcp-Session-Id` when supplied, otherwise `sha256(agent + UA + IP)` with no
time component, so it stays stable across the window just like the human UUID. A client's burst
of calls collapses to one visitor; distinct clients stay distinct.

### Searches count intents, not keystrokes

The reader's search box fetches results on a short keystroke debounce. Logging a `search` event
for every served query inflated the **Searches** card several-fold — typing `analytics` would
log eight events (`a`, `an`, `ana`, …) for one search. The debounce is a *fetch* throttle, not
an analytics trigger.

<Note>
  Search now logs a single search **intent** via a beacon on settle, result-click, or close —
  collapsing a refinement chain down to the one query the user meant. A query that extends or
  trims the pending one is treated as the same evolving search; only a topic switch commits a
  new event. This mirrors how Algolia/DocSearch separate searches from result clicks and
  collapse keystroke-level queries server-side.
</Note>

## Data model

Every assistant turn logs:

```
{ tenant, ts, question, toolsUsed, retrievedPages, answer,
  status: answered | deflected | unanswered, feedback,
  source: human | agent, sessionId }
```

The assistant overview cards, the usage chart, the categories, and the content gaps all derive
from this. Analytics is backed by a first-party events table (an `analytics_event` table with
an `agent` name column), respecting `noindex`/privacy rules and per-tenant retention.

## What runs on your docs site — and what doesn't

Everything on this page is **first-party**: your readers' pageviews are counted by Papervine and
stored in Papervine. No third-party analytics or session-replay script is loaded on a documentation
site.

If you self-host, two optional integrations exist for the **operator's own** surfaces, and both
stop at the tenant boundary by design:

| | Where it runs | Where it never runs |
| --- | --- | --- |
| Vercel Analytics | The marketing pages and the dashboard | Any documentation site |
| LogRocket session replay (`NEXT_PUBLIC_LOGROCKET_APP_ID`) | Marketing, sign-in, onboarding and the dashboard | Any documentation site |
| Chatwoot live chat (`NEXT_PUBLIC_CHATWOOT_TOKEN`) | Marketing and the dashboard | Any documentation site |
| Google Ads conversion tag (`NEXT_PUBLIC_GOOGLE_ADS_ID`) | Marketing, sign-in and onboarding | Any documentation site |

The advertising tag is the strictest of the four: on a documentation site it would attach a
third-party advertising cookie to *your readers* and report their behaviour to *your* ad account,
which is a consent decision only they can make. It is off unless you set the id, and off outside
production even then.

Session replay records the page, network activity and console, so pointing it at a documentation
site would mean recording *your readers* — which is why it stops at that boundary. It is off unless
you set the environment variable, and it masks every form input: these pages hold real credentials,
from your GitHub token and reader-auth signing secret to the password on the sign-in form.

The chat launcher is the operator's own support inbox, so it stops at the same boundary for a
second reason: on a documentation site it would invite *your readers* to open conversations
with the operator, and it would compete with your own
[AI assistant](/features/ai-assistant) launcher for the same corner of the page.
