title: Operator
description: The operator's cross-tenant overview — every customer organization, its members, sites, deploys, and traffic, on one read-only page.
---

If you run a Papervine deployment, the **platform admin** page at **`app.{your-domain}/admin`**
shows every customer on it at a glance:

- **Platform totals** — customers (organizations), users, sites, and all-time deploys, plus the
  total analytics events recorded in the last 30 days.
- **One card per organization** — its members (email and role), and a table of its sites: status
  (live/draft), connected repo, custom domain, deploy count, last deploy time, and 30-day
  analytics volume. Site names link straight into that site's dashboard.

The overview itself is **read-only**. From it, a platform admin has two ways into a customer's
world, with different power levels:

## Browsing a customer's dashboard

Site links on the admin page open that site's regular dashboard. As a platform admin you can open
**any** organization's dashboard — not just ones you're a member of. You browse **as yourself**:
an amber **"Platform admin view"** banner marks the cross-tenant context, and because you hold no
role in the organization, every manage control (invites, renames, danger zone) stays hidden and
every mutation stays blocked. Eyes, not hands.

## Impersonating a user

Each member chip on the admin page has an **impersonate** action. It signs you in *as that user*
for up to an hour: you see exactly their dashboard, their role, their sites — and actions you take
are performed **as them**. A persistent amber banner shows who you're impersonating with a
**Stop impersonating** button that returns you to your own session and the admin page.

Use browsing for "what's on this account?"; use impersonation for "what does this user actually
see, and why can't they do X?". Impersonating another platform admin is not allowed.

## Who can open it

Access is controlled by the **`PLATFORM_ADMIN_EMAILS`** environment variable: a comma-separated,
case-insensitive list of account emails.

```bash
PLATFORM_ADMIN_EMAILS=you@example.com,ops@example.com
```

- A signed-in user whose email is on the list sees a **Platform admin** link at the bottom of the
  dashboard sidebar, and can open `/admin` directly.
- Anyone else gets a **404** — the page is invisible, not forbidden.
- If the variable is unset (the default), the page is a 404 for **everyone**.

There is no in-app way to grant or revoke platform admin: changing the list means changing the
deployment's environment and redeploying. That's deliberate — the allowlist can't be escalated
through the app itself.

One nuance for impersonation: it's powered by an `admin` role on the user record that Papervine
**syncs from the allowlist** (granted when an allowlisted admin uses the admin surface, revoked at
the next sign-in of anyone no longer listed). The env var remains the source of truth — the role
column is plumbing, never something you set by hand.

## Reserved organization slugs

Because `/admin` (and a few other control-plane paths) live beside the `/:org` dashboard URLs,
those names can't be used as organization slugs: `admin`, `preview`, `app`, `api`, `login`,
`signup`, `onboarding`, and `accept-invite`. Creating an organization whose name slugifies to one
of these is rejected with a clear error — pick a different name.

## The Papervine badge on customer sites

Every tenant docs site below Enterprise renders a small **Powered by Papervine** link at the
bottom of the page. Which plans carry it is a plan **entitlement** (`whiteLabel`), not something
compiled in — so moving it to another tier is an edit to `catalog.json` followed by
`billing:sync`, with no deploy.

Two behaviours worth knowing when someone reports it looks wrong. A subscription stays pinned to
the plan version it was bought on, so an Enterprise customer whose version predates the
entitlement is handled by falling back to the plan itself — they never see the badge. And if the
database is briefly unreachable the badge is **hidden** rather than shown, because putting it on
a white-labelled site is a worse failure than leaving it off a Free one.

## The waitlist

The marketing home's primary button opens a two-field form — an email address, and an optional
line about what the person is hoping to use Papervine for. Signups land under
**Operator → Waitlist**, newest first, with the note and the page they submitted from.

The note is the column worth reading. It's free text rather than a set of categories on purpose:
before launch, the useful thing is how people describe their own problem, which is the language
your marketing copy should be using back at them.

The form is public and unauthenticated, so it carries the defences that surface needs: each
visitor can submit a handful of times per ten minutes, and a hidden field that only automated
submissions ever fill is discarded silently. Signing up twice with the same address updates the
existing entry rather than creating a second one, and a second visit can only add to what's
recorded — leaving the note blank the second time keeps the first answer.

<Note>
  Entries are never emailed anywhere. The Waitlist page is the only place they surface, so make
  it part of whatever rhythm you already have for checking the console.
</Note>

## The marketing home's live demo

The marketing home page carries a **Try it** section built from working product rather than
screenshots. It has two halves that need something from you, and one that doesn't.

The framed demo shows a **real docs site** you can read, search and browse, with an **Edit this
page** button that swaps the frame over to the visual editor. The editor half runs entirely in the
visitor's browser and needs no setup. The framed site is chosen by convention: the site with the
slug `starter` if one exists — preferred because the forkable example ships an OpenAPI spec, so
the frame includes a working API console — otherwise the `docs.` site described below. If neither
exists, the frame shows a placeholder and everything else still works.

The **Ask the assistant** chips talk to a real docs site through the
[embeddable widget](/features/assistant-widget), so they need one to point at.

It finds that site **by convention rather than configuration**: the home page looks for the site
whose custom domain is `docs.` followed by your apex — `docs.example.com` for a platform served at
`example.com`. In practice that's your own dogfooded documentation. There is no environment
variable to set.

Three things have to be true for the chips to become live, and they're all ordinary site settings:

<Steps>
  <Step title="A site claims the docs domain">
    Connect `docs.{your apex}` as that site's [custom domain](/guides/custom-domain).
  </Step>
  <Step title="Its widget is on">
    **Settings → Widget → Availability**, which is off by default.
  </Step>
  <Step title="The home page's origins are authorized">
    Add every origin the marketing home is served on under **Authorized domains** — both
    `https://{apex}` and `https://www.{apex}` if you serve both. Origins are matched exactly.
  </Step>
</Steps>

Until all three hold, the section still renders: the questions become plain links into the
documentation page that answers each one. That's also what visitors see if the database is
briefly unreachable, so a misconfiguration here degrades quietly rather than breaking the page.

<Note>
  The demo's answers are metered against the organization that owns the docs site, like any other
  widget traffic — and each visitor is rate limited, so an unusually busy day on the home page
  can't drain the account.
</Note>
