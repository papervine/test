Papervine renders a fast, themeable documentation site from a folder of **MDX + a
`docs.json`**, in a format that is a **drop-in for existing `docs.json` + MDX repos**. Point
it at an existing `docs.json` repo and it renders unchanged; self-host it anywhere.

<Note>
  These docs are written in Papervine's own format and render in Papervine itself. The
  source lives in [`docs/`](https://github.com/papervine/papervine/tree/main/docs) and is
  crawled in CI as a renderer regression test. If you can read this page, the dogfood works.
</Note>

## What it is

- **Own your docs.** MDX files in your repo, rendered by software you control. Your content
  is always just files — there is no proprietary store to get locked into.
- **Compatible with existing `docs.json` projects.** Papervine reads the same `docs.json` +
  MDX, matching its navigation schema and behavior so real repos migrate unchanged. We
  smoke-test against real-world docs repos.
- **Multi-tenant.** One deployment serves many docs sites — each at `{slug}.papervine.io`,
  a custom domain, or a path-based fallback (`/sites/{slug}`).

## Core principles

These three rules drive most of the architecture. When in doubt, they win.

<CardGroup cols={1}>
  <Card title="Never let one unsupported feature 500 a page">
    Unknown MDX components degrade to their children; a compile failure renders an inline
    notice, not a 500. A single bad page must not take down the site.
  </Card>
  <Card title="Config is a compatibility layer: warn, don't throw">
    A single unexpected `docs.json` field must never break the site. Every field is lenient;
    unknown keys pass through with a warning.
  </Card>
  <Card title="Match the source format, don't guess">
    `docs.json` is compatible with existing `docs.json` projects so real repos migrate
    unchanged. When unsure how something should behave, check it against a real-world
    `docs.json` repo.
  </Card>
</CardGroup>
