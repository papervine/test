Papervine reads the same `docs.json` + MDX format used by other documentation platforms. For
most repositories, migrating means connecting the repo and changing a DNS record — the
content itself doesn't change.

## Try it before you commit

Connect the repository as a new site. You get a complete, working copy at a Papervine
address while your current site keeps serving its own traffic untouched. Nothing about
migrating is irreversible until you move DNS.

Better still, run it locally first and change nothing at all:

```bash
npx papervine dev
```

## What carries over

<CardGroup cols={2}>
  <Card title="Your content">
    MDX files render as-is. Frontmatter, headings, links, images and code blocks behave the
    same.
  </Card>
  <Card title="Your navigation">
    `docs.json` groups, tabs, and anchors are read directly. No re-authoring.
  </Card>
  <Card title="Your components">
    Callouts, cards, tabs, steps, accordions, code groups and frames are all supported.
  </Card>
  <Card title="Your API reference">
    An OpenAPI spec still generates one page per operation, with a live "Try it" panel.
  </Card>
</CardGroup>

## What to check

Migration is usually uneventful, but these are the things worth a look:

**Components from the long tail.** The common set is supported. Something unusual renders
as its contents rather than failing — you get a plainer block, not a broken page. Skim
your most component-heavy pages and see if anything reads oddly.

**Config keys that aren't acted on yet.** Unknown keys are accepted with a warning rather
than rejected, so your site builds either way — but a setting that silently does nothing is
worth knowing about. The [config reference](/rendering/config) lists what's honored.

**Redirects.** If your current platform maintains a redirect map, that doesn't come across
automatically. Inventory it before cutover so old inbound links keep landing.

**Anything generated by your old platform's CLI.** Files it produced from other sources
aren't reproduced by connecting the repo.

<Tip>
  A fast, high-signal check: connect the repo, then click through your ten most-visited
  pages side by side with the current site. That finds real problems far quicker than
  reading a compatibility list.
</Tip>

## Cutting over

<Steps>
  <Step title="Connect the repository">
    Your existing site keeps serving. Nothing is affected yet.
  </Step>
  <Step title="Review the Papervine copy">
    Compare your highest-traffic pages, your API reference, and search results.
  </Step>
  <Step title="Add your domain in Papervine first">
    Enter the custom domain and let the certificate issue **before** you change DNS. Doing
    it in this order means the certificate is ready when traffic arrives. See
    [using your own domain](/guides/custom-domain).
  </Step>
  <Step title="Change the DNS record">
    Point the record at Papervine. Readers move over as the change propagates; there's no
    moment where the domain serves nothing.
  </Step>
  <Step title="Keep the old site up briefly">
    Leave it running for a day or two. If anything surfaces, reverting is a DNS change back.
  </Step>
</Steps>

## What you gain

Beyond parity, connecting the repo turns on things that need no authoring work:

- **[Full-text search](/features/search)** across every page, heading, and code block.
- **An [AI assistant](/features/ai-assistant)** grounded in your content, with citations —
  and an [embeddable widget](/features/assistant-widget) for your own product.
- **[MCP servers](/features/mcp-servers)**, so your docs are usable as a tool inside Claude,
  Cursor and similar.
- **[Insights](/control-plane/analytics)**, including a humans-versus-agents view of who is
  actually reading you.
- **[Studio](/control-plane/editor)**, browser editing with an AI agent, publishing as
  commits or pull requests.

## If your docs aren't in this format

Papervine renders MDX plus a `docs.json`. Coming from a different system — a static site
generator, a wiki, a Word-shaped process — the content itself is the work, and the shape to
convert to is one `.mdx` file per page with `title` and `description` frontmatter, plus a
`docs.json` listing them. [Writing content](/guides/authoring) covers the target format.
