Papervine is a multi-tenant **docs platform**: it renders a docs
site from a Git repo of MDX + a `docs.json`. This page is the contract for how to work in the repo —
follow it for every change. Start with the [architecture](/architecture) overview for the
big picture, and [renderer internals](/rendering/internals) for how MDX actually renders.

## First run

```bash
npm install
cp .env.example .env.local
npm run dev
```

That's the whole setup. `npm run dev` brings up the local services, the app, and the
automations worker together, and every layer it can't reach degrades on its own — you get a
working docs renderer and dashboard immediately.

**The AI features need one more choice**, because there's no sensible default: they stay
switched off (returning a clear "not configured") until you pick a profile in `.env.local`.
The free one runs on your own machine:

```bash
brew install ollama          # or download from ollama.com; Linux: curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3.5          # ~6.5 GB, and it's the smallest model that reliably drives our agents
```

Then uncomment **Profile A** in `.env.local` and restart. If you'd rather use a hosted
provider, uncomment Profile B or C instead and add a key. See
[Local AI models](/local-ai) for what local models can and can't do well —
briefly: they handle the assistant comfortably, and automation runs slowly but correctly.

<Note>
  Working on the renderer, the dashboard, or anything that isn't AI? Skip the model setup
  entirely. Those surfaces don't need it, and the test suites (`npm test`,
  `npm run test:unit`) run without any AI configuration at all.
</Note>

## Definition of done

A feature or fix is not done until **all** of these pass. State plainly what you ran and
what passed — if something is unverified, say so.

<Steps>
  <Step title="Typecheck is clean">
    `npm run typecheck` — TypeScript strict, no errors.
  </Step>
  <Step title="The smoke test is green">
    `npm test` boots the real renderer against fixtures and asserts no page 500s.
  </Step>
  <Step title="A regression test exists for what you changed">
    At the right layer — unit, smoke, or e2e. See [testing](/contributing/testing).
  </Step>
  <Step title="Verified in a real browser">
    Screenshot the affected page (`agent-browser`, light **and** dark mode if visual).
    Don't claim a UI change works from the DOM alone — layout bugs (e.g. the Card `h-full`
    height bug) only show visually.
  </Step>
  <Step title="Renderer / config / nav changes: crawl a real-world docs repo">
    `node tests/crawl.mjs <cloned-docs-repo>` — expect 0 × HTTP 500.
  </Step>
  <Step title="Control-plane / authed changes: e2e is green">
    `npm run test:e2e` (needs docker Postgres + MinIO up).
  </Step>
</Steps>

<Tip>
  Regression protection is a hard requirement, not optional. If you added a pure helper,
  unit-test it. If you fixed a render bug, add a fixture. See [testing](/contributing/testing)
  for which layer fits.
</Tip>

## Driving the app to test it

When a change needs hands-on verification (DoD step 4, or someone says "go test this"),
don't hand-walk signup → onboarding. Seed a known account and drive a real browser.

<Steps>
  <Step title="Bring up local infra">
    ```bash
    docker compose up -d        # Postgres (+pgvector) + MinIO (S3)
    ```
  </Step>
  <Step title="Seed known accounts">
    ```bash
    npm run db:seed
    ```
    `scripts/seed-dev.mjs` creates two logins, both password **`password`** —
    **`dev@papervine.local`** (owner) and **`dev2@papervine.local`** (admin) — as members of
    the same org, plus a connected site `starter` (→ a real-world docs repo) with activity +
    analytics data. The second account is there so you can log in as both (two browser
    profiles) and exercise real-time collab. It is idempotent (re-run to refresh the
    passwords) and **prod-guarded** — it refuses any non-localhost `DATABASE_URL`.
  </Step>
  <Step title="Log in on the app host">
    The control plane lives on the **`app.` host**. Log in at
    **`http://app.localhost:3000/login`**; the dashboard is at bare
    **`app.localhost:3000/:org/:site`** (seed → `app.localhost:3000/dev-org/starter`). New
    site at `/:org/connect`.

    Any dev port works: when `:3000` is busy (several worktrees running at once), Next
    auto-picks `:3001`/`:3002`… and auth follows — development trusts `localhost`,
    `*.localhost`, and `127.0.0.1` on **any port** (`trustedOrigins` in `src/lib/auth.ts`),
    so sign-in works without touching `BETTER_AUTH_URL`. Production never trusts these
    wildcards.
  </Step>
  <Step title="Open the rendered docs">
    Tenant docs render at **`{slug}.localhost:3000`** (subdomain mode) or **`/sites/{slug}`**
    (apex path mode). `resolveTenantSlug` picks the mode off the `Host` header; `isAppHost`
    picks the control plane.
  </Step>
</Steps>

<Note>
  The apex (`localhost:3000`) is marketing + docs and bounces auth paths to the app host.
  The marketing home is written for people new to docs platforms — it explains Papervine
  as a documentation website for your product. Terms like `docs.json`, MCP, and `llms.txt`
  live in these product docs, not on the storefront. Its header and footer link out to
  the public CLI repo. Drive everything with **`agent-browser`** (the repo standard —
  `open` / `snapshot -i` / `click @eN` / `fill` / `screenshot`; it navigates
  `app.localhost` and `{slug}.localhost` fine) or Playwright. This is the same loop that
  catches per-request content-source bugs: connect a repo, open its docs, confirm the
  sidebar and pages are the tenant's, not the platform's.
</Note>

### Testing the GitHub App locally

Most work needs none of this — the connect form's access-token path covers public and
private repos without an App. Set one up when you want to exercise what only the App
provides: installation-scoped access, push-triggered auto-sync, and publishing from Studio.

Only the **webhook** needs to be publicly reachable. The App's Setup URL redirects your
*browser*, so `http://app.localhost:3000/api/github/setup` works untunnelled — and that
callback is what ties an installation to an organization. GitHub's servers, though, POST
webhooks directly, and they can't reach your machine.

Start a channel at [smee.io](https://smee.io), use its URL as the App's **Webhook URL**, and
put the same URL in `.env.local`:

```
GITHUB_APP_WEBHOOK_PROXY_URL=https://smee.io/your-channel
```

`npm run dev` picks it up and runs the forwarder as a `smee` layer, the same way it forwards
Stripe webhooks when those are configured.

<Warning>
  **Don't skip the relay once `GITHUB_APP_ID` is set.** Publishing from Studio deliberately
  hands the sync to the push webhook whenever the App is configured, so with no relay running
  a publish commits to GitHub and then your site stays stale until someone hits **Re-sync** —
  which looks like a broken publish rather than a missing webhook. `npm run dev` prints a hint
  when it sees the App configured without a proxy URL, for exactly this reason.
</Warning>

## Database migrations (GitOps)

The schema is **versioned** — every change is a committed SQL migration, never a live
`push`. Pushing the migration *is* shipping it.

<Steps>
  <Step title="Edit the Drizzle schema">
    `src/lib/db/schema.ts` is Better Auth (regeneratable); `src/lib/db/app-schema.ts` is
    our tables.
  </Step>
  <Step title="Generate the migration">
    ```bash
    npm run db:generate
    ```
    Writes `drizzle/NNNN_*.sql` (+ `meta/`). **Commit it** and review the SQL like any code.
  </Step>
  <Step title="Apply it locally">
    ```bash
    npm run db:migrate
    ```
    CI's e2e rebuilds `papervine_test` from these same files, so a broken migration fails CI.
  </Step>
  <Step title="Prod applies on deploy">
    `vercel.json`'s build command runs `drizzle-kit migrate` before `next build`, so each
    Vercel preview migrates its own Neon branch. No manual prod steps, no `push --force`.

    Production deploys from CI once the tests pass, not on the push itself — see
    [the CI gate](/contributing/testing#the-ci-gate).
  </Step>
</Steps>

<Warning>
  Destructive changes (drop / rename) need care: generate, **read the SQL**, and prefer
  expand-then-contract. Drizzle's journal lives in a separate `drizzle` schema — a full
  local reset is `DROP SCHEMA public CASCADE; DROP SCHEMA drizzle CASCADE; CREATE SCHEMA
  public;` then migrate.
</Warning>

## Command reference

```bash
docker compose up -d        # local Postgres (+pgvector) + MinIO (S3) — `npm run dev` does this for you
npm run dev                 # the whole stack: docker services, the app, and the automations
                            # worker (cron ticks and runs execute only while it's connected).
                            # Peripheral layers attach when you've configured them — Stripe
                            # webhook forwarding starts only if STRIPE_SECRET_KEY,
                            # STRIPE_WEBHOOK_SECRET, and the `stripe` CLI are all present;
                            # GitHub webhook forwarding (smee) only if GITHUB_APP_ID and
                            # GITHUB_APP_WEBHOOK_PROXY_URL are.
                            # Every layer degrades independently: no docker → no-DB mode, no
                            # Trigger.dev login → automations just don't execute.
npm run dev:app             # just the Next server (renderer-only work)
npm run dev:fresh           # kill the dev server, wipe .next, restart clean (use when chunks/manifests are corrupted)
                            # Tests can run WHILE the dev server is up: each harness builds into
                            # its own directory (.next-smoke / .next-crawl / .next-e2e) via
                            # NEXT_DIST_DIR, so they never share output or fight over the lock.
npm run build               # production build
npm run typecheck           # tsc --noEmit
npm test                    # smoke: renderer + control-plane gate (zero-dep, no DB)
npm run test:unit           # vitest — pure-logic unit tests
npm run test:e2e            # playwright — authed journeys (needs docker Postgres + MinIO)
npm run db:generate         # generate a versioned SQL migration from schema changes
npm run db:migrate          # apply migrations to the local dev DB (reads .env.local)
node bin/papervine.mjs dev <dir>     # preview any docs repo locally
npm run prepack --workspace papervine     # rebuild the published CLI's prebuilt server
node tests/crawl.mjs <dir>           # crawl a real repo, report rendered/degraded/500
```

<Warning>
  `apps/cli` serves a **prebuilt** server, so a change to the renderer — a component, a theme
  token, a stylesheet — is invisible to `papervine dev` until you rebuild it. The CLI warns when
  its build is older than your sources, but the rebuild is yours to run.
</Warning>


## Conventions

- **TypeScript strict, App Router / RSC.** Server components by default; add `"use client"`
  only for interactivity (see `src/components/mdx/Tabs.tsx`, `Accordion.tsx`).
- **Match the surrounding code** — its style, comment density, and naming. Comments explain
  *why* (especially the [gotchas](/contributing/gotchas)), not *what*.
- **Keep `SPEC.md` and `GAP-REPORT.md` current** when you make an architectural decision or
  change what renders — record the decision and the measured result.
- **Don't commit unless asked.** When you do, end commit messages with the `Co-Authored-By`
  trailer already used in this repo's history.

<Info>
  Two principles guide every renderer change: **never let one unsupported feature 500 a
  page** (unknown components degrade to their children; compile failures render an inline
  notice), and **config is a compatibility layer — warn, don't throw**. `docs.json` is
  compatible with existing `docs.json` projects, so real repos migrate unchanged. When unsure
  how something should behave, check against a real-world `docs.json` repo rather than guess.
</Info>
