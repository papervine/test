Regression protection is a hard requirement, not optional (it's part of the
[definition of done](/contributing/working-on-papervine#definition-of-done)). There are
three layers, and the rule is simple: **put the test where the logic lives.**

<CardGroup cols={3}>
  <Card title="Unit (Vitest)">
    Pure functions, no infra. `tests/unit/` · `npm run test:unit`
  </Card>
  <Card title="Smoke (zero-dep)">
    The real renderer + control-plane gate, no DB. `tests/smoke.mjs` · `npm test`
  </Card>
  <Card title="E2E (Playwright)">
    Authed journeys against real Postgres + MinIO. `tests/e2e/` · `npm run test:e2e`
  </Card>
</CardGroup>

## Unit — `tests/unit/`

```bash
npm run test:unit
```

Pure logic, no DB or browser: `resolveTenantSlug`, `parseRepoInput`, `slugify`, lenient
config parsing. Fast — runs anywhere.

<Tip>
  If you add a pure helper, unit-test it — and keep it pure. `"use server"` files can't
  export sync helpers, so extract the logic (e.g. into `src/lib/slug.ts`) where a unit test
  can reach it directly.
</Tip>

## Smoke — `tests/smoke.mjs`

```bash
npm test
```

The renderer + control-plane **gate**. It boots the real renderer against `tests/fixtures/`
— a docs repo that reproduces every fixed bug — and asserts each page returns **200, never
500**, with the expected content. Zero-dep and no Postgres, so it runs in CI everywhere.

<Note>
  **To cover a new renderer case, add a fixture.** Drop it under `tests/fixtures/`, register
  it in `tests/fixtures/docs.json` nav, and add a check to `CHECKS`. Fixtures reproduce the
  *actual failure shape* — object favicon, `languages` nav, `.md` pages, unknown and
  member-expression components, malformed frontmatter, snippet imports, hidden pages,
  standalone cards, OpenAPI endpoints, search, the assistant route, and the Card height bug.
</Note>

DB-free control-plane checks (gate redirects, auth pages rendering in the platform theme)
live alongside the renderer checks in `CONTROL_PLANE_CHECKS`.

## E2E — `tests/e2e/`

```bash
npm run test:e2e        # needs docker Postgres + MinIO up
```

Authed control-plane journeys against a dedicated `papervine_test` Postgres + MinIO:
signup → onboarding → connect repo → dashboard, plus the logged-out gate. `globalSetup`
creates, migrates, and truncates the test DB; `auth.setup.ts` logs in once and saves the
session (storageState) so specs start authenticated.

<Warning>
  Tag any spec that hits the network (e.g. the GitHub connect flow) `@external` so CI can
  `--grep-invert @external` and stay deterministic.
</Warning>

## Real-repo crawl

```bash
node tests/crawl.mjs <dir>
```

Used to validate against real-world `docs.json` repos. It reports rendered / degraded / 500
counts and exits non-zero on any 500 — run it for every renderer, config, or nav change.
Compatibility findings vs. real-world `docs.json` repos are tracked in `GAP-REPORT.md`.

## Clean-room CLI package test

```bash
npm run test:cli
```

Run this for any change to what the published [CLI](/cli) ships — `apps/cli`, the renderer's
declared dependencies, or the packaging script.

It packs the real `papervine` tarball, audits its contents, installs it into a temporary
directory **outside** the repository, and then serves the `docs/` folder through the installed
binary, asserting that pages, the stylesheet, and docs-repo assets all come back.

The reason it exists is that every other layer runs with the monorepo's own `node_modules` in
scope, which hides a whole class of failure that appears *only* once a package is installed
from a tarball: a dependency that was used but never declared, a file the packaging step
dropped, or something from the surrounding repository accidentally compiled in. Those all pass
unit, smoke, and e2e, and then fail on a user's first run. This is the only layer that can see
them, so it gates releases.

It runs a full production build, so it's slow and deliberately not part of `npm test`.

## The CI gate

CI lives in `.github/workflows/ci.yml` and has two jobs — keep both green. A third job, in
`.github/workflows/mirror.yml`, runs after them.

| Job | Runs | Services |
| --- | --- | --- |
| `verify` | typecheck + unit + build + smoke + example-site crawl + clean-room CLI package | none |
| `e2e` | Playwright (skipping `@external`) | Postgres |
| `deploy-production` | deploys the app to Vercel — only on a push to `main`, only after both jobs above pass | none |
| `mirror` | publishes the CLI and the example docs site to their public repos, once per target, gated on CI passing | none |

**Deploying is one of the gates.** Vercel's Git integration used to deploy the moment it saw a
commit, in parallel with CI and unaware of it — so a failing run and a live production deploy of
the same commit could coexist, and a failed `next build` was the only thing that ever stopped a
bad one. Automatic deploys are now off for `main` (`vercel.json` → `git.deploymentEnabled`), and
`deploy-production` is the only route to prod. Branch and PR previews still deploy on push, which
is what previews are for.

Releases are gated too, by a publish workflow that reruns these checks before shipping so a
version tag can never publish a broken package.

Mirroring and releasing are separate steps on purpose. The mirror pushes `main` to the public
repos and nothing else — it never pushes tags — so the public source keeps up with the monorepo
on its own, while shipping to npm stays a deliberate act: tag a version in the public CLI repo,
which is what its publish workflow waits for. The practical effect is that a release tag
describes code that is already public, rather than a snapshot someone had to remember to push.

<Info>
  Migrations are part of the test story: they're versioned SQL committed to `drizzle/`,
  reviewed like code, and applied by `drizzle-kit migrate` locally, in CI's e2e (which
  rebuilds `papervine_test` from the same files), and in prod on deploy. A broken migration
  fails CI. See the [GitOps migration flow](/contributing/working-on-papervine#database-migrations-gitops).
</Info>
