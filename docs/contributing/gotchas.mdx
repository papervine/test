description: Hard-won pitfalls — JSX runtime matching, peer-dep workarounds, flex-height bugs, host rewrites, and the host-only session cookie — with the why and the fix.
---

These are learned the hard way. Each one cost real debugging time; the *why* matters as much
as the fix, because every one of them passes the obvious check and fails somewhere subtle.

### dev/prod JSX runtime must match

<Warning>
  Compile (`serialize`) and `run()` must use the **same** `development` flag and runtime, or
  React 19 throws *"production element rendered in development"*.
</Warning>

This is why we left plain `next-mdx-remote` for the hybrid renderer. See
[renderer internals](/rendering/internals) for the full compile-then-run design.

### The third-party MDX serializer package has a broken peer dep

<Warning>
  The MDX serializer package declares a peer dep on `@radix-ui/react-popover@^19.2.1`, which doesn't
  exist. **Fix:** `.npmrc` sets `legacy-peer-deps=true`. Keep it.
</Warning>

### MDX packages must be in `serverExternalPackages`

<Note>
  The MDX packages have to be listed in `serverExternalPackages` (`next.config.mjs`) or they
  fail to compile inside the Next bundle.
</Note>

### Percentage heights + flex stretch

<Warning>
  `h-full` resolves against the nearest definite-height ancestor. A stretched flex item
  (e.g. `<article>`) can hand a card full-page height — this bit the Card component.
  **Fix:** put `items-start` on content rows so children don't stretch.
</Warning>

This is a *visual* bug — it passes the DOM check and only shows in a screenshot, which is
why [definition of done](/contributing/working-on-papervine#definition-of-done) requires a
real-browser screenshot for UI changes.

### A literal HTML element in MDX bypasses the components map

<Warning>
  `<video src="/x.mp4">` written in a page compiles to a bare `_jsx("video", …)`, so a components-map
  override for `video` is never consulted — and it fails *silently*. Only markdown-emitted elements
  and capitalized components go through the map. **Fix:** a remark plugin retags the element to a
  capitalized synthetic name (`PvImg`, `PvVideo`) and the map renders the real tag back.
</Warning>

Two traps when adding one. Register the override **unconditionally** — a renamed element with no
map entry falls through to the unknown-component fallback and disappears from the page. And bump
the `mdx-compile-vN` cache key: it's content-addressed on the page source, so a cached compile
keeps emitting the old output and the change looks like it did nothing.

This is why video 404'd on every surface that sets an asset base — path-based serving and the
editor's draft preview — while a markdown image on the same page worked.

### Never hand a mutable handle to a TipTap `configure()`

<Warning>
  `Extension.configure()` merges options with a **deep** merge, which recurses whenever the
  default and the supplied value are both plain objects. A React ref is `{ current }`, so it gets
  *copied* — the extension reads its own object forever while React writes to the original.
  **Fix:** pass a function (`onKeyDown(props)`, `getAwareness()`), which is copied by reference.
</Warning>

Nothing errors and nothing warns, which is what makes this expensive: the editor's `/` command
menu ignored the arrow keys and <kbd>Enter</kbd> for as long as it existed, and the symptom read
as a focus problem rather than a wiring one. Arrows reached the document instead of the menu,
which moved the cursor out of the `/query` and so closed the menu; <kbd>Enter</kbd> reached the
document too, leaving the mouse as the only way to choose an item.

It also hides from casual inspection, because `options` is a getter that re-merges on every
access — read it directly and it looks right. The damage is that extension code captures it
**once**, at editor construction (`const opts = this.options` in `addProseMirrorPlugins`), and
that snapshot never sees a later write.

### Portalled overlays render outside the `.db` shell

<Warning>
  Dialogs, dropdown menus, and the mobile nav drawer use a Radix portal, so their content
  mounts at the end of `<body>` — **outside** the `.db` PlatformShell. There it inherits none
  of the platform CSS variables, so `--fg` / `--card` / the brand fonts resolve to nothing and
  the panel renders invisible or unstyled. **Fix:** the overlay carries a `.db-portal` class —
  the same palette and fonts as `.db` but *without* its layout (`position: relative`,
  `min-height: 100vh`, solid background), which would otherwise fight the fixed overlay. The
  platform font variables also sit on `<body>` (not just `.db`) so they resolve in the portal.
</Warning>

Reach for `.db-portal` (not the full `.db` class) on anything a control-plane component portals
to `body`. Applying the whole `.db` shell there breaks the fixed overlay's positioning.

This is also why the platform light/dark signal — `data-db-theme` — lives on **`<html>`**, not
on the `.db` element: the portalled overlays sit at `<body>`, *outside* `.db`, so a theme attribute
on `.db` wouldn't reach them. On `<html>` it covers both `.db` and `.db-portal`. The value is
written pre-paint from `localStorage['pv-theme']` (a `<script>` in the root layout), so a reload in
light mode never flashes dark.

<Warning>
  Don't theme the platform with hardcoded `bg-white/[0.06]`-style overlays — on a light background a
  translucent *white* is invisible. Use the **ink channel** instead: `bg-[rgba(var(--ink-rgb),0.06)]`,
  which is white on dark and black on light at the same opacity. The `--fg` / `--muted` / `--line` /
  `--card` tokens already flip with the theme; reach for those for text and borders.
</Warning>

### Tests fetch `127.0.0.1`, not `localhost`

<Note>
  Tests fetch `127.0.0.1`, and the dev server binds to `0.0.0.0`. Some runners resolve
  `localhost` to IPv6 `::1` while Next listens on IPv4 — using `127.0.0.1` sidesteps the
  mismatch.
</Note>

### Node doesn't resolve `*.localhost` — browsers do

<Warning>
  `app.localhost` works perfectly in Chrome and fails with `getaddrinfo ENOTFOUND` from anything
  using Node's DNS: Playwright's `APIRequestContext`, and the `papervine` CLI. **Fix:** address
  `127.0.0.1` from Node and leave the `app.localhost` URL to the browser.
</Warning>

This bites in two places that look unrelated. An e2e spec can drive a page on `app.localhost`
and, in the same test, fail to `request.post` the same host — so API calls in
`tests/e2e/device-auth.spec.ts` go to the apex, which serves the same `/api/auth/*` route tree.
And `papervine login --url http://app.localhost:3000` dies before sending a byte, which is why
local sign-in uses `--url http://127.0.0.1:<port>` while the browser page it opens is still on
`app.localhost`.

<Note>
  Neither failure explains itself, because **`fetch` reports every transport problem as the bare
  string `fetch failed`** and hides the real one on `.cause` — DNS, refused connection and TLS
  all read identically. Unwrap `err.cause.message` before showing a network error to anyone.
</Note>

### A better-auth plugin can require an option TypeScript says is optional

<Warning>
  A plugin's options may be typed `Partial<…>` while its runtime Zod schema declares a field
  **without** `.optional()` — `deviceAuthorization`'s `schema` is one. Omitting it throws a
  ZodError *while `src/lib/auth.ts` is being imported*. **Fix:** pass `schema: {}`.
</Warning>

The failure mode is what makes this expensive. Typecheck passes. The app then 500s every page
that reads a session while every page that doesn't renders perfectly, so it looks like a
regression somewhere unrelated — here the tell was an unknown-widget-id 404 becoming a 500, in a
route nobody had touched. After adding any auth plugin, load a page that reads a session, and
keep `npm test` in the loop: the smoke gate catches this because it exercises pages on both sides
of that line.

### Redirecting to a tenant host needs a hard navigation

<Warning>
  A server-action `redirect()` (or `router.push` / `<Link>`) into a tenant or app-host URL
  **skips the middleware Host rewrite**. **Fix:** the server returns the target
  (`{ ok, redirectTo }`) and the client does `window.location.assign(redirectTo)`.
</Warning>

Tenant pretty-URLs (`{slug}.papervine.io/…`) and the bare app-host dashboard URLs
(`app.papervine.io/:org/:site`) exist only as a `middleware.ts` Host-rewrite (to
`/sites/{slug}/…` and `/app/:org/:site`) — no route file backs them. A soft RSC nav resolves
against the *real* route tree and skips that rewrite, so `redirect("/")` lands on the apex
marketing home, not the tenant's docs. It passes `curl` and SSR (a hard request rewrites
fine) and only fails in a real browser. This bit reader-auth login and the app-host
dashboard's post-create / post-login landings.

<Info>
  **Nuance:** an intra-dashboard `<Link>` or `router.push` *within* the app host is fine — it
  already carries the rewrite context. It's the **cross-context** hop (apex → app, or a
  server-action redirect into a rewritten path) that drops it. Plain `redirect()` is fine for
  genuine apex routes (the marketing pages) — there's nothing to rewrite there.
</Info>

### The marketing apex can't see the app-host session — by design

<Warning>
  The Better Auth session cookie is **host-only** on `app.papervine.io` and is never shared
  to `.papervine.io` — doing so would send your auth token to every tenant docs subdomain, an
  XSS-exfil surface. Don't "fix" a missing dev label by sharing the real session cookie.
</Warning>

So `www` shows a Dashboard link via a *benign* `pv_signed_in=1` flag cookie
(`src/lib/signed-in-flag.ts`), set on the parent domain by the app-host middleware and read
by the marketing nav. Because it reaches tenant subdomains (parent-domain cookie), it's
**httpOnly** (+ Secure in prod) so tenant page JS can't read it, and it's cleared
**server-side in the middleware** on logout (a client clear can't touch httpOnly).
Logged-in users who hit `/login` or `/signup` on the app host go straight to the dashboard —
**unless the URL carries a `?redirect=`**, which means they arrived mid-flow (approving a
`papervine login`, resuming a GitHub App install) and the thing they came to finish is at that
path. Same-host paths only, via `safeRedirect`; forwarding an arbitrary origin from a login page
is an open redirect that hands over a freshly authenticated visitor.

<Note>
  **Dev caveat:** Chrome rejects `Domain=localhost` cookies, so the flag (and thus `www`'s
  Dashboard link) only works in prod (`.papervine.io`). The redirect-to-dashboard behavior
  works everywhere.
</Note>
